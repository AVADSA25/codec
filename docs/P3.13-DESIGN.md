# P3.13 — Push to the phone for approvals, questions, briefing and agent results

Item 5 of docs/UI-PHASE2-3-PLAN.md. Builds on P2.14's service worker.

## Why

When CODEC needs an answer (an approval, a question from an agent) or an agent finishes, the owner only learns it
by opening the PWA. The owner decided on 2026-09-29 that CODEC's own channel is Web Push: no outside chat app is
needed, everything stays in CODEC and a web browser. Telegram stays an optional bridge, not the default.

## What

- **`codec_push.py`** (new, stdlib + the existing `cryptography` and `requests`; no new dependency):
  - VAPID key pair (P-256). The private key lives in the Keychain as `ai.avadigital.codec.vapid_private_key`
    (via `codec_keychain`), created once by the dashboard under a file lock; senders only read it.
  - Payload encryption per RFC 8291 (`aes128gcm`), VAPID per RFC 8292 (ES256 JWT, 12 h expiry).
  - `notify(kind)`: the fan-out. Never raises, never blocks the caller (sends from a daemon thread), at most one
    push per kind per 60 s per process, and nothing when push is off or no device is subscribed.
  - The push carries no content. The payload is `{"kind", "title", "body", "url"}` taken from a fixed table in
    the module; callers pass only the kind, so no question text, agent name or chat text can reach a push service.

    | kind | line | opens | Settings switch |
    |---|---|---|---|
    | `approval` | CODEC needs your approval | `/` | Approvals |
    | `question` | CODEC has a question for you | `/` | Questions |
    | `briefing` | Your briefing is ready | `/` | Morning briefing |
    | `agent_done` | An agent finished its work | `/tasks#reports` | Agent results |
    | `agent_blocked` | An agent needs your go-ahead | `/tasks#reports` | Agent results |
    | `agent_stopped` | An agent stopped | `/tasks#reports` | Agent results |
    | `test` | Notifications are on | `/` | always |

  - Devices and switches in `~/.codec/push.json` (0600, atomic write, cross-process lock): up to 10 devices, each
    with its endpoint, keys, a label made from the browser's user agent ("iPhone Safari"), and when it last worked.
    A device the push service reports gone (404 or 410) is removed.
  - Endpoints must be https on a known push service (Google `fcm.googleapis.com`, Mozilla `*.push.services.mozilla.com`,
    Apple `*.push.apple.com`, Microsoft `*.notify.windows.com`); anything else is refused, so a stored endpoint cannot
    make the Mac post to an arbitrary host. No redirects are followed.
  - Kill switch: `PUSH_ENABLED=false` stops all sending.
- **Where pushes come from** (the fan-out runs where the notification is posted):
  - `codec_ask_user.ask()` after the question notification: `approval` for strict-consent questions (destructive
    actions, MCP-over-HTTP consent), `question` otherwise.
  - `codec_agent_messaging.post_message()` after the banner (not when the agent is silenced): `agent_done`,
    `agent_blocked`, and `agent_stopped` for `agent_aborted`.
  - `briefing`: the switch and the kind exist now; the Morning briefing item (P3.x, later in the queue) calls
    `notify("briefing")`.
- **Routes** (`routes/push.py`, behind the dashboard login like every `/api` route):
  - `GET /api/push`: public key, switches, device list (id, label, dates; never the endpoint).
  - `POST /api/push/subscribe`, `POST /api/push/unsubscribe`, `POST /api/push/types`, `POST /api/push/test`.
- **Service worker** (`static/sw.js`): `push` shows the notification from the payload (fallback line when the
  payload is missing; the URL must be a same-origin path); `notificationclick` focuses an open CODEC window and
  opens the URL there, or opens a new one.
- **Shell** (`static/codec-shell.js`): `CodecShell.push` (state, turn on, turn off, test). On each page load, if
  the owner turned push on for this device and the browser dropped the subscription, it is renewed quietly (the
  permission is already granted); a changed endpoint is re-sent.
- **Settings** (Home, Settings, General): a "Phone notifications" section: the state for this device, Turn on or
  Turn off for this device, Send a test, the four switches, and the device list with Remove. On iPhone and iPad it
  explains that CODEC must be added to the Home Screen and opened from there first (iOS 16.4 or later).

## Not in this item

The Morning briefing itself (a later item). Telegram changes. Pushing scheduler results, heartbeat alerts or the
shift report (not in the plan's list).

## API or schema change

New routes above. New file `~/.codec/push.json`. New Keychain entry `ai.avadigital.codec.vapid_private_key`.
New audit events `push_subscribed`, `push_unsubscribed`, `push_sent` (metadata only: kind, device counts,
results; never an endpoint), listed in docs/codec-architecture.md. No database change.

## Test plan

tests/test_push.py:
- Encryption matches the RFC 8291 Appendix A example byte for byte, and a random-key round trip decrypts.
- The VAPID header verifies with the public key; `aud` is the endpoint's origin, `exp` within 24 h.
- Only known push-service hosts over https are accepted; bad keys are refused.
- The payload for each kind is exactly the fixed table entry; unknown kinds send nothing.
- `notify` respects the switches, the throttle, the kill switch and "no devices"; it never raises.
- A 410 removes the device; a 201 records `last_ok`; the file stays 0600; endpoints never reach the audit log.
- `ask()` sends `approval` for strict consent and `question` otherwise; `post_message` maps agent types and
  skips silenced agents.
- Routes: subscribe, list (no endpoint in the reply), types, unsubscribe, test.
- The service worker's `push` and `notificationclick` handlers under Node (payload shown, fallback line,
  foreign URL refused, window focused or opened).

Browser (throwaway dashboard): the Settings section in each state, the switches save, Turn on asks for permission.
The browser pane cannot reach a real push service, so a real phone test is left for the owner: add CODEC to the
Home Screen, turn on, Send a test.

## Rollback

Revert the PR. `~/.codec/push.json` and the Keychain entry can stay (unused) or be deleted by hand; a device that
was subscribed stops receiving anything because nothing sends.
